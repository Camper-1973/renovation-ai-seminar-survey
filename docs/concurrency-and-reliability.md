# GAS公開ツールの同時アクセス・保存信頼性ナレッジ

## 対象

GAS + HTML Service + Googleスプレッドシートを使う公開ツール全般。
特に、自己診断ツール、概算見積もりシミュレーター、セミナー用診断など、短時間にアクセスが集中する可能性があるフォーム系ツールを対象とする。

## 今回の不具合から得た原則

### 1. ロックは「保存の瞬間」だけ

`ScriptLock` はGAS全体の共通ロックであり、RDBの行ロックではない。
診断計算、入力検証、シート取得、集計などをロック内に入れず、回答1件の追記など競合しうる最小処理だけをロックする。

悪い例：
- ロック取得
- シート初期化
- 診断計算
- 回答保存
- 全件集計
- ロック解除

推奨：
- 入力検証
- 診断・概算計算
- 保存先準備
- ロック取得
- 1件保存
- 即ロック解除
- 結果返却

### 2. 送信時に全件走査しない

保存直後に回答数を数えるため全行を読み直す、毎回ヘッダーを確認する、書式を設定する、といった処理は同時アクセス時のボトルネックになる。
集計はダッシュボード側や別処理で行い、送信のホットパスから外す。

### 3. 回答ごとに一意なIDを持つ

通信エラーやタイムアウトでは、サーバー側では保存成功しているのにブラウザが成功レスポンスを受け取れない場合がある。
その状態で再送すると二重登録になるため、1回の回答ごとに `responseId` を持たせる。

再送時も同じ `responseId` を利用し、すでに存在する場合は再INSERTせず成功扱いにする。これにより送信処理を冪等化する。

### 4. 一時的な失敗は限定回数だけ再試行

同時アクセス、Spreadsheetサービスの一時的な遅延、通信失敗などは短時間で回復することがある。
保存処理は無限再試行せず、2〜3回程度に限定して短い待ち時間を挟んで再試行する。

ただし、入力不正や設定不足など再試行しても直らないエラーは即時終了する。

### 5. エラーを握りつぶさない

利用者には診断結果をできるだけ見せたい一方、保存に失敗した事実まで隠すと、会場30人に対して集計15件しかない、といった欠損に気づけない。

「結果生成」と「保存成功」は内部的には分けて管理し、管理側で保存件数・失敗件数を確認できる設計を優先する。

### 6. 直接編集されるスプレッドシートをDB同等に扱わない

スプレッドシートにはRDBのような行ロック、ユニーク制約、COMMIT/ROLLBACK、トランザクション分離がない。
列削除、並び替え、見出し変更などの人為操作でもアプリが壊れうる。

公開規模が大きくなった場合は、スプレッドシートは閲覧・分析用に残し、一次保存先を本来のDBへ移すことを検討する。

## 公開前の標準チェック

- 同時送信時にロック範囲が最小か
- 送信処理内に全件走査がないか
- `responseId` 等による重複防止があるか
- 一時エラーの限定再試行があるか
- 再試行によって二重登録されないか
- 保存失敗を管理側で検知できるか
- 5人、10人、20人、可能なら50人程度の同時送信テストを行ったか
- 成功率、失敗率、p50/p95応答時間、重複件数、欠損件数を確認したか

## スケール判断

### スプレッドシート継続でよいケース

- 追記中心
- 数十人規模の同時利用
- データ量がまだ小さい
- 人がシートを直接確認・集計したい
- 厳密な複数テーブル取引がない

### DB移行を検討するケース

- プレスリリースや広告で瞬間的に大量アクセスが来る
- 数百〜数千件規模の短時間書き込みが想定される
- 複数データを一括で整合性を保って更新したい
- ユニーク制約やトランザクションが必要
- 保存失敗や重複が事業上許容できない
- 集計量が増えスプレッドシート読み取りがボトルネックになる

## 次の候補

第一候補は Cloud Firestore。公開Webツールの回答1件を1ドキュメントとして保存しやすく、`responseId` をドキュメントIDとして使えば重複防止をDB側の設計に寄せられる。大量アクセスへのスケールもしやすい。

SQL的な整合性、複雑なJOIN、厳密なトランザクションが重要なら Google Cloud SQL + Apps Script JDBC を検討する。

Notion Databaseは業務閲覧・ナレッジ管理には便利だが、公開フォームの一次保存先としてはAPIレート制限や外部API依存があるため推奨しない。

## 運用方針

今後、自己診断ツール・概算見積もりシミュレーター・セミナー診断などの公開GASツールを改修する際は、このチェック項目を共通の非機能要件として扱う。
